# @ai-assistant/daemon

The local daemon of the assistant (Phase 1). One Node process on `127.0.0.1` that

- serves the web app (`apps/web/dist`) and a REST + WebSocket API that implements the `ApiClient` contract of `packages/shared`;
- hosts the **Secretary lane** (`@ai-assistant/agent-core`): chat with Claude through the Agent SDK, tool permissions as approval cards, spend budgets;
- receives **Claude Code http hooks** and projects them into a live monitor of terminal and IDE sessions (the Work screen);
- hosts **embedded terminals** (your own `claude` and a shell on a PTY, each in its own host process, off until you switch them on; the highest-risk surface, see [Terminal](#terminal));
- hosts the **stage backend** (the live 3D assistant: the character, her wardrobe and mood, the scene she lives in, a speech pipeline, and the `mira-stage/1` socket that any renderer connects to; on by default, see [Stage](#stage));
- keeps operations state in SQLite (sessions, events, tasks, approvals, chat, audit, usage, and the stage) and settings in a small key-value table.

Everything else (brain, calendar, mail, finance, world, briefing) is still fixture data behind the same snapshot, see [What is real and what is mock](#what-is-real-and-what-is-mock).

The default backend is the **zero-token fake**. It never contacts Anthropic. Real Claude needs `CLAUDE_BACKEND=sdk` (see [Unverified](#unverified-and-known-limits): that path has not been exercised against the live API).

## Run it

```
pnpm install                                   # once, from the repo root
pnpm --filter @ai-assistant/web build          # optional: lets the daemon serve the UI
pnpm --filter @ai-assistant/daemon start       # tsx src/main.ts
```

The startup banner prints the one-time sign-in link and says loudly when the fake backend is active:

```
Mira daemon 0.0.0
  Listening   http://127.0.0.1:7421  (loopback only)
  Sign in     http://127.0.0.1:7421/?code=...#tp=...
              open this once; it works for 15 minutes and only one time
  Data dir    C:\Users\you\AppData\Roaming\ai-assistant
  Backend     FAKE: scripted replies, zero tokens, no network. Nothing here talks to Claude.
```

Open the link in the browser you will use (use the same host name, `127.0.0.1` or `localhost`, afterwards: cookies are per host). The web app must read `?code=`, `POST /api/auth/exchange` it, then remove it from the URL (`history.replaceState`) so it does not stay in the history. Restart the daemon for a new link; the browser session itself lasts 30 days and survives restarts. The part after `#` is the **terminal pairing**: a second secret, new at every start, that only embedded terminals need (see [Terminal](#terminal)). A fragment is never sent to any server; the page keeps it in its own origin's storage and removes it from the address bar. Open the **whole** link in the browser you will use terminals in.

`Ctrl+C` (SIGINT, SIGTERM, SIGHUP (the signal of a closed terminal window, and of a closed console on Windows) and SIGBREAK on Windows) shuts down gracefully: interrupt and stop the lane, stop the timers, kill every embedded terminal and its process tree, wait for the PTY host processes to leave, close the WebSocket clients (code 1001), drain pending hook events, close the database. A second signal forces exit.

### Environment

All read once at startup by `src/config.ts` (a pure function of the environment, unit-tested). Invalid values stop the daemon with a clear message that never echoes secrets.

| Variable | Default | Meaning |
|---|---|---|
| `DAEMON_PORT` | `7421` | Port on `127.0.0.1`. There is deliberately no way to bind another interface. Fails fast if taken. |
| `DATA_DIR` | Windows `%APPDATA%\ai-assistant`; otherwise `$XDG_DATA_HOME` or `~/.local/share` + `/ai-assistant` | Database, secrets, agent scratch folder. |
| `CLAUDE_BACKEND` | `fake` | `fake` (scripted, zero tokens) or `sdk` (real Agent SDK). |
| `CLAUDE_AUTH_MODE` | `api-key` | `api-key` or `local-login` ([ADR 0001](../../docs/adr/0001-claude-auth-modes.md)). Changeable in Settings; takes effect for the next lane session (restart). |
| `CLAUDE_CONVERSATION` | `fresh-daily` | `fresh-daily`: a new Claude conversation each local day and after a daemon restart, carried by the stored memory in the system prompt and a short seed of recent chat (cheaper: a resumed history is re-read on every turn and only grows). `resume`: one stored conversation resumed for ever (renewed daily). Forgetting something she remembered ends the current conversation in both modes. |
| `OPEN_BROWSER` | unset | `1` opens the sign-in link in your default browser at start (best effort; the link is printed either way). `start.cmd` and `scripts/start.sh` set it. Only the daemon's own `http://127.0.0.1` link is ever opened. |
| `ANTHROPIC_API_KEY` | none | Read only in `config.ts`, kept non-enumerable (never in JSON or logs), passed to the SDK backend in `api-key` mode. |
| `CLAUDE_EXECUTABLE` | SDK-bundled binary | Path to your own `claude` for `local-login`. The daemon never reads or proxies OAuth tokens. Also the program the embedded "Claude" terminals run (else a PATH search). |
| `DEMO` | off | `1` keeps the fixture sessions, tasks, approvals and events so the Work screen is populated. Runs on a separate, disposable `demo.db` that is recreated at every start. |
| `WEB_DIST` | `apps/web/dist` | Static files to serve (used only if `index.html` exists there). |
| `DEV_ORIGINS` | `http://127.0.0.1:5173,http://localhost:5173` | Extra allowed `Origin`s (the Vite dev server). |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error`, `silent`. Every line is secret-masked. |
| `BUDGET_SECRETARY_USD`, `BUDGET_READER_USD`, `BUDGET_VOICE_USD`, `BUDGET_GLOBAL_USD` | 4, 1, 1, 10 | Daily budgets (API-equivalent estimates). Spend is persisted, so a restart does not reset the day. |
| `STALE_RUNNING_MINUTES` | `10` | A `running` hook session with no event for this long becomes `stale`. |
| `STALE_IDLE_MINUTES` | `360` | Same for `idle`, `waiting_input` and `blocked_permission` sessions. |
| `RETENTION_DAYS` | `30` | Finished hook sessions and raw events older than this are deleted. |
| `CLAUDE_CONFIG_DIR` | `~/.claude` | Used only by the hook installer CLI. |
| `TERMINAL_MAX` | `4` | Running embedded terminals at once (1 to 16). Each runs in its own PTY host process (about 70 MiB resident), see [PTY host processes](#pty-host-processes). |
| `TERMINAL_IDLE_MINUTES` | `240` | A running terminal with **no client attached** is closed after this long (1 to 10080). An attached terminal is never idle-closed. |
| `TERMINAL_SCROLLBACK_KB` | `256` | Per-terminal output ring buffer replayed on attach (16 to 4096). Memory only. |
| `TERMINAL_ALLOW_DEV_ORIGINS` | off | `1` lets the Vite dev server's origin (`DEV_ORIGINS`) use terminals. Off by default, see [Terminal](#terminal): developing the terminal UI against `pnpm dev` needs it. |
| `TERMINAL_CLAUDE_COMMAND` | none | **Test only.** A program (or a JSON array `["node","script.js"]`) that "Claude" terminals run instead of your `claude`. The daemon logs a warning when it is set. |

There is no environment variable that turns embedded terminals on: only the switch in Settings does (see [Terminal](#terminal)).

### Developing the web app against the daemon

The daemon sends no CORS headers, so the browser must see one origin. Proxy through Vite (this config now lives in `apps/web/vite.config.ts`, target from `DAEMON_URL`):

```ts
server: {
  host: '127.0.0.1', port: 5173,
  proxy: {
    '/api': { target: 'http://127.0.0.1:7421', changeOrigin: true },
    '/ws':  { target: 'ws://127.0.0.1:7421', ws: true, changeOrigin: true },
  },
},
```

`changeOrigin: true` is required: the daemon rejects any `Host` other than `127.0.0.1:PORT` or `localhost:PORT`. The `Origin` the browser sends (`http://127.0.0.1:5173`) is in the dev allowlist. Embedded terminals are the exception: they accept only the daemon's own origin, so using them through the dev server needs `TERMINAL_ALLOW_DEV_ORIGINS=1` on the daemon (see [Terminal](#terminal)).

## Security model

Threats: any web page can reach `127.0.0.1` (DNS rebinding, CSRF, cross-site WebSocket hijacking); other local software; secrets inside hook payloads. See [ARCHITECTURE section 10](../../docs/ARCHITECTURE.md). Implemented in `src/security.ts` and `src/http/guards.ts`, tested in `test/security.test.ts`, `test/ws.test.ts`, `test/static.test.ts`.

**Order of checks, on every request:**

1. `Host` must be exactly `127.0.0.1:PORT` or `localhost:PORT` (case-insensitive), else `403 forbidden_host`. Applies to static files and hooks too.
2. `Origin`: required and allowlisted on every non-GET browser request and on WebSocket upgrades; on GET it may be absent but, if present, must be allowlisted; on the hook route it may be absent (not a browser) but, if present, must be allowlisted. Allowlist = `http://127.0.0.1:PORT`, `http://localhost:PORT`, plus the dev origins. Else `403 forbidden_origin`.
3. Mutating routes (POST, PUT, PATCH, DELETE) need `Content-Type: application/json` (a body-less request without a type passes), else `415`. The hook route is exempt: its auth is a bearer token, and the headers Claude Code really sends were not verified, so it parses leniently and fails open.
4. Authentication: browser routes need the session cookie (`401`); the hook route accepts **only** `Authorization: Bearer <hook token>` (a cookie does nothing there, and the hook token does nothing on browser routes). Tokens in query strings are never read. `POST /api/auth/exchange` is the only open API route and is rate limited for WRONG codes (10 failures per minute, then `429`); the correct code is always accepted, so nobody can lock the owner out by hammering the endpoint (the code has 256 bits: the limit only keeps a flood cheap and quiet).

**Secrets** live in `DATA_DIR/secrets.json` (mode `0600` where the OS honours it): a 256-bit random hook token, and the SHA-256 of each browser session token (never the token itself). All comparisons are constant time (both sides hashed to equal-length digests, `crypto.timingSafeEqual`). A running daemon notices a hook token rotated on disk (`hooks token --rotate`). On Windows the file is protected only by the user profile ACLs; **Windows Credential Manager via `@napi-rs/keyring` is the planned upgrade** and is not implemented. On POSIX the data folder is created `0700` (an existing one that holds `secrets.json` or the database is tightened to `0700`; any other folder you point `DATA_DIR` at keeps its permissions), the database and its `-wal` and `-shm` files are `0600` (the empty file is created first so SQLite gives its side files the same mode) and `agent/` is `0700`. The session list is re-read when `secrets.json` changes on disk (the `revoke` command below), and every write re-reads it first, so a revocation made from the command line is never written over.

**Browser session:** the printed link carries a single-use exchange code (256-bit, expires in 15 minutes). `POST /api/auth/exchange {code}` swaps it for an opaque cookie `aia_sid_<port>`: `HttpOnly; SameSite=Strict; Path=/; Max-Age=30 days`. `Secure` is not set because the daemon is plain http on loopback.

**Signing out and revoking.** `POST /api/auth/signout` (cookie, `Origin` and JSON like every mutation; the body is optional) ends this browser's session, clears the cookie and is audited; `{"everywhere": true}` ends every session. `pnpm --filter @ai-assistant/daemon exec tsx src/cli/revoke.ts [--dry-run]` ends every session from the command line (audited into the daemon's database; it never prints a token or a hash; the hook and stage tokens are rotated by their own commands). A running daemon notices the changed file on its next request, and closes the live `/ws` and terminal sockets of the revoked sessions (`4401`) at once when a browser signs out, and at the next heartbeat (30 s) when the command line did it; the terminals' processes keep running. The app does not call `signout` by itself yet (there is no button); after `revoke`, restart the daemon for a new sign-in link.

**Headers:** no CORS headers at all, on any response. Every response gets `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy: same-origin`, a `Permissions-Policy`, and `Cache-Control: no-store` on API responses. HTML gets the CSP:

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
connect-src 'self' ws://127.0.0.1:PORT ws://localhost:PORT; img-src 'self' data: blob:;
worker-src 'self' blob:; media-src 'self' blob:; font-src 'self' data:; object-src 'none';
form-action 'self'; frame-ancestors 'none'; base-uri 'none'
```

(MediaPipe or any WebAssembly later needs `'wasm-unsafe-eval'` in `script-src`: add it when that lands.)

**Privacy:** hook payloads are redacted before they are stored or logged (`src/store/redact.ts`): `tool_response` becomes a 300-character masked preview plus its size, `tool_input` keeps its structure with strings cut to 300 characters, prompts to 200, whole payloads capped at 16 KB; strings are masked for `sk-ant-...`, other API keys, GitHub and Slack tokens, AWS keys, JWTs, `Bearer`/`Basic` credentials, PEM private keys, `key=value` pairs whose key looks secret, plus every secret the daemon holds, verbatim (`Security.secretLiterals`): the hook token, the stage token, the pending sign-in code, the session tokens this run issued (kept in memory only, for this), the terminal pairing and the API key. The daemon's logger (the one `main.ts` now uses; it used to inject one that knew only the API key) applies the same list to every line and also masks `aia_sid_<port>=...` cookie values and `?code=...` by shape. Masking runs before truncation so a secret cannot leak as a prefix. Logs carry no payloads, prompts or message text; the audit log records that a chat message was sent, never its text. The static handler never serves outside `dist` (decoded, backslashes treated as separators, resolved, re-checked after symlinks).

Not covered: other software running as the same Windows user can read `secrets.json` and the database (rely on BitLocker and profile permissions); the SQLite file is not encrypted.

## API

All routes except `/api/auth/exchange`, static files and `/hooks/*` need the session cookie. Errors are `{ "error": "<code>", "message": "...", "details"?: [...] }`. Request bodies are validated with the zod schemas in `packages/shared/src/daemon.ts` (`400 invalid_request` / `invalid_json`, `413` above 512 KB; a body without a declared `Content-Length`, for example a chunked upload, is read under the same cap, and a bodiless `DELETE` passes).

| Route | Purpose |
|---|---|
| `GET /api/health` | `DaemonHealth`: version, epoch, uptime, backend, lane state, hooks received, last hook time, session count, data dir. `hooksReceived` counts since process start. |
| `GET /api/snapshot` | A full `Snapshot` (validates against the shared schema) with `seq` = the bus's latest seq. Header `X-Daemon-Epoch` carries the epoch for `/ws`. |
| `POST /api/auth/exchange` | `{code}` -> sets the session cookie (open, rate limited for wrong codes). |
| `POST /api/auth/signout` | Optional `{everywhere?: boolean}`: ends this browser's session (or every session), clears the cookie, closes the session's sockets, audited. Cookie auth like every browser route. Not in the shared contract; nothing in the app calls it yet. |
| `POST /api/chat` | `{text, modality}` -> `202 {accepted}` after `lane.send`. `503` if the lane is down, `502` if the lane refuses. |
| `POST /api/chat/interrupt` | Barge-in. `202`. |
| `POST /api/approvals/:id/decision` | `{decision: approved \| denied \| rejected}` (`rejected` = `denied`). Lane approvals go to `lane.decideApproval`; fixture-backed ones (demo, proposals) resolve like `FixtureClient`. **`409 not_answerable_here`** for approvals seen through hooks: hooks are non-blocking, so such a permission can only be answered in that terminal. `409 already_resolved`, `409 stale_approval` (the turn is gone, the card is closed as denied), `404`. |
| `POST /api/proposals/:id/decision` | Fixture-backed (the real vault is Phase 2). Updates the proposal, resolves the linked approval, no commit is invented. |
| `GET/POST /api/tasks`, `PATCH or PUT /api/tasks/:id`, `DELETE /api/tasks/:id` | Persisted kanban. PATCH takes `{column?, title?, description?, priority?}`. DELETE has no incremental event in the contract, so it publishes a `snapshot.reset`. |
| `PUT /api/settings/trust/:ruleId` | `{mode: ask \| auto}`. `409 locked` for locked rules (money, strategy, persona). |
| `PUT /api/settings/claude-mode`, `/guest`, `/webcam`, `/persona` | Persisted in `kv`. POST is accepted as an alias for PUT. Persona edits apply immediately and are audited (the lock on "change her own persona" is about Mira editing herself). |
| `DELETE /api/learned/:id` | Forget a learned fact (persisted). |
| `GET/POST /api/terminals`, `GET/DELETE /api/terminals/:id`, `POST /api/terminals/:id/ticket`, `GET /ws/terminal/:id` | Embedded terminals. **403 `terminals_disabled` until switched on.** See [Terminal](#terminal). |
| `PUT or POST /api/settings/terminals` | `{on}`: the switch. Persisted, audited, `settings.terminals.enabled` in the snapshot; switching off kills every running terminal. |
| `GET /api/stage`, `PUT or POST /api/settings/stage`, `DELETE /api/stage/connection`, `POST /api/stage/assets`, `PUT /api/stage/characters/select`, `PUT .../:id/params`, `PUT .../:id/presence`, `POST .../:id/equip`, `.../unequip`, `.../outfit/apply`, `.../outfit/save`, `.../outfit/delete`, `.../outfit/suggest`, `POST /api/stage/scene/preset`, `POST /api/stage/scene/objects`, `PUT or PATCH` and `DELETE /api/stage/scene/objects/:id`, `PUT /api/stage/scene/camera`, `GET /api/stage/memory`, `DELETE /api/stage/memory/:id`, `DELETE /api/stage/memory?confirm=all` | The stage backend, see [Stage](#stage). Cookie auth like every browser route. |
| `GET /ws` | WebSocket, see below. |
| `GET /ws/stage` | The stage socket for an engine or the simulator: **bearer stage token, never the cookie**. See [Stage](#stage). |
| `POST /hooks/:event` | Claude Code hooks. Bearer hook token only. Always answers `200 {}` first, processes afterwards. |
| `GET *` | Static files from `apps/web/dist` with SPA fallback (HTML navigations only) and the CSP. Without a build, `/` shows a placeholder page. |

Every mutation writes an audit entry and publishes the matching `ServerEvent` (`chat.*`, `avatar`, `session.update`, `agent.event`, `approval.new/resolved`, `task.update`, `proposal.update`, `settings.update`, `learned.update`, `snapshot.reset`, and `stage.live` for the stage backend).

### WebSocket

`/ws?since=<seq>&epoch=<epoch>`: needs the session cookie, an allowlisted `Origin` (required: every browser sends it) and a valid `Host`; nothing is read from the query string except `since` and `epoch`. Limits: 8 clients (`503` beyond), 64 KB messages, ping every 30 s (a client that misses a pong is dropped), a client whose unsent buffer passes 4 MB is dropped (slow consumer). Clients are read-only (`{type:"ping"}` is answered with `{type:"pong"}`). A page served from a dev origin (the Vite dev server, which shares the cookie) may read the feed, but what it receives carries nothing about terminals unless `TERMINAL_ALLOW_DEV_ORIGINS=1`: the terminal list of a `snapshot.reset` is empty and the audit entries about terminals ("Opened a terminal", "Closed a terminal", ... with the terminal id in the target) are removed from the settings of a `snapshot.reset` and of a `settings.update`; REST responses carry no CORS headers, so a foreign page cannot read those at all. A socket whose session was signed out or revoked is closed with `4401`.

The first message is the shared `WsHello` plus a local flag: `{type:"hello", seq, epoch, backend, version, resync, reason?}`.

**Resume rule.** `seq` is monotonic per process; the ring buffer holds the last 2000 events.

| Request | Result |
|---|---|
| no `since` | live events only, `resync:false` |
| `since` + same `epoch`, inside the buffer | the missed events are replayed right after the hello, `resync:false` |
| different `epoch` (daemon restarted) | `resync:true, reason:"epoch"`, nothing replayed |
| `since` older than the buffer | `resync:true, reason:"gap"` |
| `since` newer than the latest | `resync:true, reason:"future"` |
| `since` without `epoch` | `resync:true, reason:"unknown_epoch"` (it cannot be verified) |

On `resync:true` the client refetches `GET /api/snapshot`, replaces its state, and ignores live events with `seq <= snapshot.seq`. Flow for a normal connect: `GET /api/snapshot` (take `seq` and the `X-Daemon-Epoch` header), then open `/ws?since=<seq>&epoch=<epoch>`; nothing published in between is lost.

## Terminal

The user can run their own `claude` and a shell **inside the app**. Under the hood the daemon starts one **PTY host process** per terminal (see [PTY host processes](#pty-host-processes)), which starts the program on a PTY (node-pty: ConPTY on Windows, forkpty elsewhere); the daemon relays its bytes to xterm.js in the Work screen (Work, Terminal). Code: `src/terminal/`, tests: `test/terminal*.test.ts`, browser side: `apps/web/src/api/terminalClient.ts` and `apps/web/src/views/work/components/TerminalTab.tsx`.

### Threat model: this is remote code execution as the user, by design

A terminal runs any command with the user's full permissions. Whoever can drive one owns the PC and the user's files, accounts and tokens. So the design assumes the following attackers and keeps the surface as small as it can be:

| Attacker | What they would try | Mitigation |
|---|---|---|
| A web page in the user's browser | Open a terminal with a cross-site request; hijack the socket (cross-site WebSocket hijacking); DNS rebinding | `Host`, `Origin` (required on every mutation and on the upgrade), `SameSite=Strict` HttpOnly cookie, JSON content type, no CORS. A socket needs a ticket on top of the cookie, and a ticket needs the pairing (below). |
| Another local program that can reach `127.0.0.1` but has no cookie | Connect to the socket | No cookie, no ticket: refused (401 on the upgrade). |
| Another local server the user browsed to (the cookie is scoped to the host, not the port, so it receives the cookie) | Replay it from a non-browser client with a forged `Origin`: mint a ticket, start a terminal, switch terminals on | **The pairing**: terminal routes also need a second secret that is not in the cookie jar (item 2b). A cookie alone gets `401 terminal_proof_required`. Shown in a real Chromium with a hostile server on another port. |
| The assistant itself (a prompt injection, a bad tool call) | Make Mira open or type into a terminal | **No tool exists for it.** Terminals are not in `TOOL_SURFACE` or `STAGE_TOOL_SURFACE`, the lane context carries no reference to them, and `test/terminal.lanes.test.ts` checks the surfaces, the lane context, the imports of the lane and tool wiring files and that driving the real Secretary lane never spawns a process. |
| A program running inside a terminal | Pick up the daemon's secrets by accident; type into or read another terminal; outlive its terminal | The child environment is the user's minus everything that belongs to the daemon (item 7); every terminal has its own PTY host, so no descriptor of another terminal is inherited (a later terminal's programs see no `/dev/ptmx`); closing ends the whole process tree (item 10). **Not covered: reading what the same OS user can read, see below.** |
| A bug that lets a client flood or stall the daemon | Memory or CPU exhaustion | Caps on terminals, frame size, input rate, text-frame rate, scrollback, unauthenticated sockets and send buffers (control replies included). |
| Someone who finds a terminal left open | Reattach later | Switching terminals off kills them all; detached terminals are closed after the idle timeout; the cookie, the pairing and a fresh ticket are needed to attach. |

Not covered: malware already running as the same Windows user (it can start any process itself and read `secrets.json`); a compromised web app bundle (XSS) would be able to type into a terminal, which is why the CSP forbids inline and foreign scripts; the user pasting a hostile command into their own shell.

**A program inside a terminal is the same OS user as the daemon, so it can read what the daemon can read.** That is `/proc/<daemon pid>/environ` on Linux (the daemon's process environment, `ANTHROPIC_API_KEY` included when you started the daemon with the key in its environment; deleting a variable from `process.env` does not wipe that initial copy), `secrets.json` (mode `0600` does not help against the same user, and it holds the hook and stage tokens), the SQLite database and, where the OS allows it, the daemon process itself (ptrace, signals). The environment scrub (item 7) stops *accidental* inheritance by the programs of a terminal; it is not a boundary against a program that goes looking, so a prompt-injected Claude in a terminal can read the chat lane's API key. This is inherent to running everything as one user and is **not fixed** (a deliberate "won't fix"). The planned upgrade is the OS credential store (Windows Credential Manager through `@napi-rs/keyring`, the macOS Keychain, libsecret) for the key and the tokens, and keeping the API key out of the daemon's process environment. Until then: give a terminal no work you would not give your own account, and prefer `CLAUDE_AUTH_MODE=local-login` (no API key in the daemon at all) if you run Claude in terminals.

The same goes for project folders: a terminal may start in a known project's root or under your home, and project roots come from the hook-discovered projects, so anything holding the (weaker) hook token can register a folder and widen where a terminal may *start*. That is accepted: a terminal is not a sandbox (a shell can `cd` anywhere you can), and the roots are not a security boundary.

### Mitigations, in the order a request meets them

1. **Off by default.** Every terminal route, including the socket upgrade, answers `403 terminals_disabled` until the user turns on Settings, Privacy, "Embedded terminals" (`PUT /api/settings/terminals {on}`). The switch is stored in `kv` (`settings.terminals`), written to the audit log and shown in `settings.terminals.enabled`. **Switching off kills every running terminal and its process tree, empties the list and drops pending tickets before the call returns.** Authentication is checked before the gate, so an unauthenticated caller learns nothing about the switch. Switching ON also needs the pairing (item 2b); switching OFF is a safety action and needs only the cookie (so a program holding nothing but a stolen cookie can switch terminals off, which ends what runs in them, but can never start, attach to or switch on a terminal: the safe direction is the one that stays easy).
2. **The ordinary request gate** (`src/http/guards.ts`) on every route: Host, Origin, JSON content type, session cookie. A plain HTTP `GET /ws/terminal/:id` also needs the cookie (`426` otherwise).
   **Own origin only.** On top of the allowlist, terminal routes, the on/off switch and the socket accept only the daemon's own origin (`http://127.0.0.1:PORT`, `http://localhost:PORT`). The session cookie is shared by every port on `127.0.0.1`, and `DEV_ORIGINS` allows `:5173` (everyone's Vite default), so without this rule any other app that happens to run on that port could mint tickets or switch terminals on. The dev server needs `TERMINAL_ALLOW_DEV_ORIGINS=1` to use them. (The rest of the API keeps the general allowlist, so the same exposure exists there for everything else; terminals are the one surface where it is remote code execution.)
2b. **The pairing: a second secret that is not a cookie.** The session cookie is scoped to the *host*, not the port, so another server the user browses to on `127.0.0.1` (a dev server, a container's published port) receives it when the user types its address or follows a same-site link, and can replay it from a non-browser client with a forged `Origin`. So terminals also need the **pairing**: a 256-bit secret, new at every daemon start and never written to disk, that the daemon prints only in the *fragment* of the sign-in link (`/?code=...#tp=...`). A fragment is never sent in a request or a `Referer`: no server sees it. The page takes it out of the address bar when it loads, keeps it in its own origin's storage (`localStorage`, key `aia.terminalProof`; another port is another origin and cannot read it) and sends it as `X-Terminal-Proof` on every terminal route and when switching terminals ON. Without it: `401 terminal_proof_required` (checked after `Origin` and the on/off gate; compared in constant time; read from that header only, never from a query string, a cookie or a body; masked by the logger). What you will notice: a daemon restart changes the pairing, so open the new link in the browser you use terminals in (the Terminal tab says so when the browser holds none, and a stale one is answered with the same message); a browser profile that only has the cookie can use the rest of the app but not terminals. What it does not cover: such a program can still read the dashboards and the terminal list in the snapshot (ids, titles, folders), it cannot run a command; and a program that can read your browser profile (a browser may keep the link you opened in its history database) or the console scrollback (the link is printed there) is the same-OS-user case above. Tested in `test/terminal.pairing.test.ts` and, in a real Chromium against a hostile server on another port, in `e2e-terminal.mjs`.
3. **Tickets** (`src/terminal/tickets.ts`). A browser cannot set headers on a WebSocket and a secret in a URL would reach history and logs, so: `POST /api/terminals/:id/ticket` (cookie, Origin, JSON, like every mutation) returns `{ticket, expiresInSec: 30}`. A ticket is 256 random bits (only its SHA-256 is kept), **single use** (presenting it consumes it, whatever the outcome), valid for about 30 seconds, **bound to that one terminal** and **to the browser session that asked** (SHA-256 of the cookie). Every pending ticket is compared with `timingSafeEqual`, no early exit. More than 20 failed presentations in a minute **by one browser session** are refused for that session (an expired ticket is not a failure: a slow client is not an attacker; one misbehaving session cannot lock the others out). Nothing is ever read from the socket URL's query string.
4. **The socket** (`src/terminal/ws.ts`). Upgrade checks: Host, Origin (required), cookie, switch on, terminal exists, at most 8 unauthenticated sockets. After the upgrade the **first frame must be a text frame `{type:"auth", ticket}` within 5 seconds**; anything else, a bad, reused, expired or foreign ticket, closes the socket with the generic reason `unauthorized` (code 4401; timeout 4408). Then `{type:"ready", replayBytes}`, the scrollback as **binary** frames, then live output. Keystrokes and output are binary frames; text frames are only the shared `TerminalClientMessage` (resize) and `TerminalServerMessage` (ready, exit, error), validated with the zod schemas in `packages/shared/src/daemon.ts`; a malformed text frame closes the socket (4400). **Text frames have a budget of their own** (burst 100, 50 a second; the page debounces resizes): an overrun closes the socket (`4429`). **Replies are bounded like output**: a socket whose queue, control replies included, passes `maxBufferedBytes` is dropped, so a client that floods valid frames and never reads cannot grow the daemon's memory. A socket that is being closed is closed once, and nothing it still sends is looked at.
5. **Limits.** `TERMINAL_MAX` running terminals (429 `terminal_limit`; slots are reserved while a process is starting, so concurrent creates cannot pass the cap). **One attached client per terminal**: a second attach is refused with `already_attached` (close code 4409). Input frames above 64 KB close the socket (1009); a token bucket on keystrokes (1 MiB burst, 512 KiB/s sustained, every frame costs at least 256 bytes so a flood of tiny frames is limited too) drops excess frames **with an `input_rate_limited` notice, never silently** (at most one notice a second, so a flood is not answered frame for frame); a client that keeps flooding anyway (20,000 dropped frames in 10 s) is closed with `4429`. Output to a client whose unsent buffer passes 1 MiB is dropped (the client is disconnected, the terminal keeps running, it can reattach and gets the replay). Scrollback: a fixed ring buffer (default 256 KB) allocated once per terminal, **in memory only, never written to disk or logged**. Ping every 30 s drops dead peers. At most 8 exited terminals stay listed.
6. **Where a terminal starts** (`src/terminal/cwd.ts`). `projectId` resolves to that project's `rootPath` (from the hook-discovered projects; the Secretary lane's pseudo project is not one). An explicit `cwd` must be an absolute path that, after `realpath` (symlinks, junctions and 8.3 names resolved with the native realpath), is a directory inside a known project root or the user's home. Refused with a stable code: UNC and device paths (`\\server\share`, `//server/share`, `\\?\...`, also when a mapped drive resolves to one), any `..` segment, relative and drive-relative paths, characters Windows forbids, alternate data streams, trailing dots and spaces, symlinks that escape. Comparison is case-insensitive on Windows. A filesystem root is never accepted as a root. **This decides where a terminal starts; it is not a sandbox**: a shell can `cd` anywhere the user can.
7. **The child environment** (`src/terminal/env.ts`): the daemon's environment (which came from the user's shell) minus: `DAEMON_*`, `AI_ASSISTANT_*` (the hook token variable), `AIA_*`, `MIRA_*`; every variable of the table in [Environment](#environment) (`DATA_DIR`, `DEV_ORIGINS`, `WEB_DIST`, `CLAUDE_BACKEND`, `CLAUDE_AUTH_MODE`, `DEMO`, `LOG_LEVEL`, `RETENTION_DAYS`, `BUDGET_*`, `STALE_*`, `TERMINAL_*`); **`ANTHROPIC_API_KEY`** (the chat lane's budgeted key: your own `claude` signs in by itself, and the daemon never hands its key to it nor silently turns a subscription login into API billing; set a key inside the terminal if you want one there); token-shaped names with a daemon-flavoured prefix (`STAGE_TOKEN`, `HOOK_TOKEN`, `EXCHANGE_CODE`, `SESSION_TOKEN`, `COOKIE_SECRET`...); and the package manager's "inside an npm script" markers when you started the daemon with `pnpm start` (`npm_lifecycle_*`, `npm_package_*`, `npm_command`, `npm_execpath`, `INIT_CWD`...). The user's own credentials stay (`AWS_SESSION_TOKEN`, `GITHUB_TOKEN`, `CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_OAUTH_TOKEN`...). `TERM=xterm-256color` and `COLORTERM=truecolor` are set. A planted secret is checked not to reach the child in both a unit test and a real-PTY test. **Module loaders of the daemon's own launcher** are scrubbed too: the pnpm and tsx shims start the daemon with `NODE_PATH` pointing at the daemon's dependencies, which would let any Node program in a terminal `require` them. `NODE_PATH` entries inside the daemon's tree (the workspace, the daemon package, a pnpm virtual store) are removed and the user's own entries stay; `NODE_OPTIONS` loses only its code-loading flags (`--require`, `-r`, `--import`, `--loader`, `--experimental-loader`, with their values) and keeps the rest (`--use-openssl-ca`, `--max-old-space-size`...). Consequence: Claude Code hooks from a Claude started inside the app reach the daemon only if the hook token is embedded in `settings.json` (`hooks install --embed-token`) or the user exports `AI_ASSISTANT_HOOK_TOKEN` in that shell themselves.
8. **Credentials.** The daemon never reads, copies, stores or proxies Claude's login. "Claude" means the user's own `claude` (`CLAUDE_EXECUTABLE`, else a PATH search that honours `PATHEXT`, empty and relative PATH entries ignored); if it is not found the API answers `422 claude_not_found` with install help. `TERMINAL_CLAUDE_COMMAND` exists only for tests.
9. **Audit** (`src/terminal/mount.ts`): enable, disable, open, close (by you, idle, switch off, daemon stopping), exit (with the exit code) and refusals (with the refusal code). Each entry has the terminal's kind and id only: **never keystrokes, output or the folder**. Logs carry ids, kinds and exit codes, never bytes.
10. **Killing.** Closing, switching off, idle close and graceful shutdown (SIGINT, SIGTERM, SIGHUP, SIGBREAK) end the terminal's whole **family**, not only its process group. On POSIX the family is the PTY child (a session leader), every process in its session, and every descendant by parent pid, read from `/proc` (a `ps` fallback elsewhere; `src/terminal/procTable.ts`) with start stamps against pid reuse. The order: SIGTERM to the leader's group and to every other member (SIGCONT to a stopped one), the PTY is hung up, the leader gets `killGraceMs` (2 s); if it is still there, SIGKILL to the whole family; then, **whether or not the leader left**, the rest of the family gets the same grace and is SIGKILLed if it is still running (a job that ignores SIGHUP and SIGTERM, `nohup`, `( cmd & )`, a nested shell with job control, the detached children of a Claude). Never signalled: pid 0 and 1, the daemon's own pid and its ancestors, a process whose pid was recycled since it was looked at. Processes that could not be ended (another user's) are counted on the audit entry of the close ("N process(es) could not be ended"). Windows: `taskkill /PID <pid> /T /F` with `execFile` and an argument array from `%SystemRoot%\System32` (never a shell string, `windowsHide`). If the daemon itself dies, the PTY host ends the tree (see below). A process `exit` handler hard-kills the families synchronously when the daemon ends without a graceful stop. **What remains:** a process that has already left the terminal for good before it ends (`setsid` and the parent exiting, a double-fork daemon, `systemd-run`, a container) is tied to it by nothing and survives; terminals are not a sandbox. Checked on Linux with 13 process shapes in `terminal.pty.test.ts` and the reviewer's 14-shape matrix (close, switch off, SIGTERM, SIGINT, SIGHUP, SIGKILL): only the two shapes that daemonise on purpose survive.
11. **The browser** loads xterm.js lazily (a separate chunk, only when the Terminal tab opens), loads no clipboard addon (OSC 52 does nothing) and no link addon, shows a permanent "runs commands as you" note that also says what is not the daemon's doing (your shell's own history file, Claude Code's own transcripts: do not type secrets you would not want there), and stores nothing except the pairing (`localStorage`, `aia.terminalProof`). **Hyperlinks a program prints (OSC 8)** are shown (xterm.js implements them by itself), but activating one never opens it directly: the page refuses everything but plain `http` and `https` addresses without a user name or password, without control, zero-width or bidirectional characters and longer than 2000 characters; it shows the real (normalised, punycode) address in the title while the pointer is over a link and asks with a native `confirm` dialog that names the host and the address; only a yes opens it, with `noopener,noreferrer`. A window drag sends one resize, not dozens.

### PTY host processes

node-pty creates every PTY master without close-on-exec. While all terminals lived in the daemon process, the master of every earlier terminal was inherited by the programs of every later one: a program in terminal B (a prompt-injected Claude opened after a shell, say) could type into and read terminal A through the inherited `/dev/ptmx` descriptor with no ticket, cookie or audit entry, and those extra copies also kept the kernel from hanging terminals up when the daemon died. So **the daemon never loads node-pty**. `src/terminal/hostClient.ts` starts one child process per terminal (`src/terminal/ptyHost.ts`: `process.execPath` under the same tsx loader, by its absolute URL, `stdio: pipe`, an environment without any daemon secret) and talks to it in a small framed protocol over the host's stdin and stdout (`src/terminal/hostProtocol.ts`: `spawn`, `write`, `resize`, `kill` one way; `spawned`, `spawnFailed`, `data`, `exit` the other; terminal bytes only inside `write` and `data` frames, never logged). It is stdin and stdout and not an IPC channel on purpose: the host's descriptors 0 to 2 are replaced by the PTY slave in the shell, so nothing of the daemon channel can reach it. Each host owns exactly one master; a shell's descriptors are 0, 1, 2 and its own (checked with a real shell in `terminal.pty.test.ts` and `e2e-terminal.mjs`: terminals 1, 2 and 3 all show no `/dev/ptmx`).

The host also outlives the daemon just long enough to clean up. When its input closes (the daemon exited, crashed or was killed with SIGKILL: the kernel closes the daemon's descriptors) or it receives SIGTERM, the host ends the terminal's whole family itself, in the same order as above, and exits. Console signals (Ctrl+C, a closed console, which reach every process of the daemon's group) are ignored by hosts: the daemon decides. A host that vanishes while its program runs is reported to the service as an exit with no code, and the daemon ends that program's family itself. A graceful daemon stop waits for the hosts to leave. The cost: one extra node process per terminal (measured on Linux: about 70 MiB resident, the tsx loader included, and about 0.1 to 0.2 s to start), so `TERMINAL_MAX` (default 4, up to 16) now also bounds that.

### Lifecycle and protocol

`POST /api/terminals {kind: "claude"|"shell", projectId?, cwd?, cols?, rows?}` returns `201` with a `TerminalInfo` (`running`). `GET /api/terminals` lists them, `GET /api/terminals/:id` reads one. `DELETE /api/terminals/:id` kills a running terminal's tree and removes it, or just removes an exited one (`204`). A terminal that ends by itself (the user typed `exit`, claude quit, a crash) stays listed as `exited` with its exit code, and a late attach still replays its last output, until it is deleted. The list is part of the snapshot (`terminals`); a change publishes a coalesced `snapshot.reset`.

Socket flow: `POST /api/terminals/:id/ticket` then `GET /ws/terminal/:id` (Upgrade) then text `{type:"auth",ticket}` then `{type:"ready",replayBytes}` then `replayBytes` of binary scrollback then live binary frames; the client sends binary keystrokes and text `{type:"resize",cols,rows}` (10 to 500, 5 to 200); the server ends with `{type:"exit",exitCode}` and closes (1000; `4401` when the session was signed out, `4429` for a flood). The browser reconnects with a **fresh ticket** and the daemon replays; the process keeps running while the browser is away.

The replay is the **recent output as bytes, not a screen snapshot**: after a reload a full-screen program (Claude Code redraws in place) shows its recent output, and the replay can begin in the middle of a line or an escape sequence once the ring buffer has wrapped.

### Windows notes (reasoned about and unit-tested with Windows-style strings, never run on Windows)

- **ConPTY** through node-pty inside the PTY host (`encoding` is not passed on Windows; ConPTY output is always a string and is re-encoded as UTF-8). The pid used for the tree kill is node-pty's inner pid (the shell or program itself). The host is started with `windowsHide` and three pipes; node-pty in a node process that has no console of its own is how other applications use it too (as far as I know VS Code's pty host works that way), but this host has never run on Windows.
- **`claude.exe` resolution**: `PATHEXT` is honoured (only `.exe .com .cmd .bat` can run), `.exe` wins over a `.cmd` shim in the same folder, `.ps1` is ignored. A `claude.cmd` (the npm shim) is started as `cmd.exe /d /s /c ""<path>""` using the System32 `cmd.exe`; a path containing `"` or `%` is refused. `CLAUDE_EXECUTABLE` may omit the extension.
- **Shell**: `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe -NoLogo` (your profile loads), else `powershell.exe` on PATH, else `COMSPEC`, else `cmd.exe`. Elsewhere `$SHELL` when absolute and executable, else `/bin/sh`.
- **`taskkill`** is the only way the tree is ended, and `/T` walks the tree as it is at that moment: a grandchild whose parent already exited is not found, and neither is a process in another job object. A Job Object with `KILL_ON_JOB_CLOSE` around the shell would be the real answer; it needs a native helper (or `ffi`) and is **not built**. `reap` (the sweep after the leader left) does nothing on Windows: a third `taskkill` on a pid that may already belong to someone else is more dangerous than the survivor.
- Paths: drive letters required, UNC refused, comparison case-insensitive; `realpath.native` is expected to return the canonical case and long names (not verified on Windows).
- A daemon killed with `taskkill /F` or a power loss gives no chance to clean up. On Linux the PTY host sees its pipe close and ends the whole tree (checked in `e2e-terminal.mjs` and `terminal.pty.test.ts`, also with SIGKILL and with a later terminal that ignores SIGHUP). On Windows the hosts are started without `detached`; libuv puts non-detached children into a kill-on-close job object (my understanding of libuv, not verified here), so a host most likely dies with the daemon before it can run `taskkill /T` on the shell, and what remains is ConPTY closing, which ends the console processes attached to it. That is no worse than before the hosts existed and it is **unverified**. A console that is closed reaches the daemon as SIGHUP, which is now handled like SIGTERM (the graceful path, which does run `taskkill` first).

## Stage

The long-term interface is a live 3D assistant in an empty "cerebral space" ([docs/CEREBRAL-SPACE.md](../../docs/CEREBRAL-SPACE.md), [ADR 0008](../../docs/adr/0008-stage-protocol-and-engine-choice.md)). **The daemon owns the character** (identity, appearance, wardrobe, scene, mood, memory, performance) and talks to a replaceable **stage** (Unreal, Unity, the web room, or the headless simulator) over the `mira-stage/1` contract (`packages/shared/src/stage.ts`). The pure logic lives in `packages/stage-core`; this section is the daemon's part: SQLite, the socket, REST, the lane wiring. Code: `src/stage/`, `src/store/stageStore.ts`, tests: `test/stage*.test.ts`, browser side: `apps/web/src/stage/` and Settings, Stage.

It is **on by default** (`PUT /api/settings/stage {on}` switches it off: no stage can connect, the stage tools answer politely, nothing is sent). With nothing connected it still works as a backend: mood, wardrobe, scene and memory exist, the dashboards can edit them, and the draft web room follows her.

### Connect a stage

1. Start the daemon. The banner prints where the socket is and **where the token lives, never the token**: `ws://127.0.0.1:PORT/ws/stage`, and `secrets.json` (key `stageToken`).
2. Read the token with `pnpm --filter @ai-assistant/daemon exec tsx src/stage/cli.ts token` (add `--rotate` to replace it; a running daemon follows a rotated file; a connected stage keeps its socket). Treat it like the hook token: do not paste it into chat, a URL or a screenshot.
3. The stage connects with `Authorization: Bearer <token>` (no cookie, no query string), sends `hello` first, then answers every command. The headless simulator does exactly this: `connectSimulator()` in `src/stage/simClient.ts` (used by the tests and by `apps/web/scripts/e2e-stage.mjs`).

### The stage socket: who may connect

Checked in this order, all **before** the upgrade completes (a plain HTTP answer, no socket is created), in `src/stage/upgrade.ts` and `security.checkStageUpgrade`:

| # | Check | Refusal |
|---|---|---|
| 1 | the peer address is loopback (the daemon only listens on `127.0.0.1`; this is the explicit second lock) | `403 not_loopback` |
| 2 | the path is exactly `/ws/stage`; anything else under it (`/ws/stage/`, `/ws/stagex`) is answered here, the browser socket handler leaves it alone | `404` |
| 3 | **no query string at all** (a token in a URL would reach logs and history): refused before anything else is read | `400 no_query` |
| 3b | the request is **HTTP/1.1** and carries `Host`, `Origin` and `Authorization` **at most once** (Node keeps the first of a duplicated header, another parser might keep the last; a request the two would disagree about is refused, not judged by one of them) | `400 http_version` / `400 duplicate_header` |
| 4 | `Host` is `127.0.0.1:PORT` or `localhost:PORT` | `403 forbidden_host` |
| 5 | `Origin` is **absent** (an engine is not a browser) or allowlisted (own origins plus `DEV_ORIGINS`) | `403 forbidden_origin` |
| 6 | `Authorization: Bearer <stage token>`, compared in constant time (both sides hashed to equal-length digests, `crypto.timingSafeEqual`). **The cookie header is never read.** | `401 unauthorized` |
| 7 | the stage switch is on | `403 stage_disabled` |
| 8 | no other stage is connected | `409 stage_busy` |

The stage token is a new secret in `secrets.json` next to the hook token (256 random bits, separate from it: neither opens the other's door). It is registered as a secret literal of the logger, so a line that held it would be masked. **The browser cookie does not work on the stage socket, and the stage token does not work on any browser route** (`401`), including the dashboards' own `/ws`; both are tested over real sockets and real HTTP, and in the real Chromium run. A plain HTTP `GET /ws/stage` answers `401` without the token and `426` with it. A Phase 1 `secrets.json` without a stage token gets one on the next start.

**One stage at a time.** A second authenticated connection is refused (`409 stage_busy`) until the first closes. A crashed engine closes its socket at once on loopback, and a half-open one is dropped by the ping (every 30 s; a missed pong drops it). "The newest wins" was rejected on purpose: it lets two stages fight forever. Settings, Stage has a **Disconnect** button (`DELETE /api/stage/connection`) for a stuck one.

After the upgrade the `StageSession` of stage-core wraps the socket: the stage speaks first (`hello`, within `hello timeout`, else `4001`), a protocol mismatch or an invalid hello is **refused and the socket closed**, nothing is sent before the hello, commands are validated and tracked until `command.done` or `command.failed`, in-flight commands are bounded, and the session adapts to the capabilities the stage declared: constructs it cannot draw (and their data) are skipped, a rig it does not support or too many characters fail with a reason, and the face comes from the backend (ARKit-52 frames) or from the stage's own audio-to-face. Limits: messages from the stage above 256 KB close the socket (`1009`), a client whose unsent buffer passes 4 MB is dropped, binary frames sent by a stage are ignored (counted), audio and face frames go out only while the transport is under its high-water mark. What a stage says is never logged: an `error` event is logged as its `fatal` flag and its length only (the message is the engine's own text and can quote speech, paths or keys), terminal input from a stage pane is dropped and counted, and `character.interact` events pass a token bucket (a burst of 10, refilled at 4 per second): the rest are counted in `hub.dropped.interact` and ignored, so a stage cannot turn them into a flood of gaze commands.

### Resume

The hub rebuilds a (re)connecting stage **from the database, never from what the stage last acknowledged**, so changes made while it was away (or before a daemon restart) are not lost: `character.load` for the active assistant and your character (outfit, sliders, voice), `scene.load` (objects, constructs, the active camera, lighting), her mood as `perform.affect`, what she was doing (idle profile, posture, gaze) when this process knows it (the stage-core mirror knows what went through an earlier connection; what the hub itself observed fills the rest, so an engine that connects minutes after the daemon started still learns that she is asleep during quiet hours instead of waiting for a change), then every construct's data as a full replace. Her mood is persisted (at most every 30 s and at shutdown) and decays from the time it was written. A daemon restart is covered by `test/stage.ws.test.ts` and by `e2e-stage.mjs` (outfit, camera, a body slider and the knowledge graph come back on a new simulator).

### REST

All routes need the session cookie, an allowlisted `Origin` on mutations and `Content-Type: application/json` (the ordinary gate). Bodies are validated with the zod schemas in `packages/shared/src/daemon.ts` (`400 invalid_request` with the field named), then by the stage-core services. Every mutation is **audited, refusals included** (outcome `blocked`, with the code), delivered to the connected stage, and announced to the dashboards with a `stage.live` event whose `rev` changed. A refused change changes nothing.

| Refusal | Status and code |
|---|---|
| a slider outside the range the base declares | `422 param_out_of_range`: "Height (cm) must be between 162 and 190 (you sent 250). The sliders are bounded to adult proportions." (stage-core would clamp silently, which hides client bugs, so the daemon **refuses**) |
| a parameter combination that reads as childlike, even when every value is inside its range | `422 adult_envelope` |
| an unknown parameter or a bad colour | `422 invalid_params` |
| taking off the last piece of a full outfit, an outfit preset that would leave her half dressed | `422 baseline` / `invalid_preset` |
| an asset whose licence does not allow personal use (or whose licence is unknown), as clothing or as a scene object | `422` with the licence in the message (`licence` for scene objects) |
| a prop worn, a piece in a slot it does not fit, a base that is not adult | `422` |
| a hostile locator (`asset:\\host\share`, `asset://host/x`, `asset:C:\x`, `pack:../x`, percent-encoded or double-encoded traversal, `file:`, `javascript:`) | `422` |
| a character base whose parameter ids the adult envelope cannot read (age or youth words under another name), or an accessory in the top, bottom or full-body slot | `422` |
| an unknown character, preset, asset, object or camera shot | `404` (`422 unknown_shot` for a shot name) |
| an id that already exists (object, catalog entry; **existing catalog entries are never replaced**) | `409` |
| the stage switch is off | `409 stage_disabled` |

`POST /api/stage/assets {manifest}` registers a catalog entry. It is **metadata only**: the stage-core catalog validates it (a character base must attest `adult: true` and its slider ranges must sit inside the adult envelope, locators cannot escape the content root and carry no credentials, the licence record must be coherent). A "not for personal use" entry is stored, shown with its licence, and unusable. **Registered entries are never vetted**: vetting (permission to be picked as her default clothing, exemption from the extra rules an unknown asset must meet) belongs to the entries this build ships, is decided in code (`seedIds()` in `src/stage/seed.ts`: the row must say `seed` AND its id must be one the build ships) and is applied again on every start, so a catalog entry that tags itself `baseline` never becomes what she wears, before or after a restart.

### What is stored (schema version 3)

`src/store/stageStore.ts` is the only SQL for the stage. Migration 3 adds: `stage_assets` (the catalog, **metadata only**, licence flags in columns plus the manifest JSON), `stage_characters`, `stage_outfit_presets` (the wardrobe presets of each character: the character row carries none), `stage_active` (the active character per role), `stage_scene` (the working scene) and `stage_scene_presets`, `stage_memory` (episodes, relationship facts and preferences with their sensitivity), `stage_mood` (one row). Settings (`settings.stage`, `stage.seeded`, the outfit director's history) are in `kv`. Migrations are tested from an empty database and from a Phase 1 (schema 2) database with data. A row that no longer validates reads as missing instead of throwing.

**The seed runs once per database** (marker `stage.seeded`): the seed catalog (30 metadata entries: three rig families of adult bases, hair, tailored dark pieces, structured outerwear, training wear, understated metal accents, two props and the void), the default assistant (named from the persona, the **AUTHORITY** presence: upright, economical, long steady gaze, measured pace, high dominance with low arousal), **your representation as an abstract, faceless form** (no face is modelled and **no face capture is used or needed**), and the empty "cerebral void" scene with two scene presets. Afterwards the database is the truth: your edits are never overwritten by a later start. On every start the characters are repaired against the catalog (an item whose asset vanished or whose licence changed is taken off, the clothed baseline is refilled from the vetted baseline pieces). **When that cannot be done safely nothing is saved**: a character whose base is gone or rejected, whose parameters the adult envelope refuses, or who cannot be validly clothed gets no `character.load`, no mood and no behaviour (the warning in the log names the character, the code and the first problem, which talk about assets and parameter names, never a payload), and comes back as soon as the cause is fixed.

### Content rules

Every character is an **adult**: slider ranges are bounded (apparent age 28 to 58 on the seed bases, height 162 to 190 cm, bounded head scale, jaw definition, eye size, roundness and leg length), the whole parameter set is judged as a combination (a combined youthfulness limit), and the daemon refuses anything outside. Seed entries and presets are tasteful and professional or athletic, and **a fully clothed baseline is always kept**: no operation (a slider, a preset, the assistant's own tool, a restore) can leave her undressed. "Clothed" means what the pieces cover (top: torso, bottom: legs, full-body: both), not which slot they are in. Nothing revealing, lingerie or sexualised exists as a default anywhere. The licence of every asset travels with it and is judged on every use; "adult expression" is a separate flag that must be explicitly true for uses that need it, and nothing in the product uses it.

### How the lane drives her

`app.ts` builds the stage **before** the lane and hands the lane factory a second argument, `{ stageTools }`, which `main.ts` merges into the lane's tools (`createStageToolBindings`: `stage_set_outfit`, `stage_set_scene`, `stage_gesture`, `stage_camera`, `character_remember`, `stage_state`; cosmetic and reversible, tiers T0 to T2, so `character_remember` asks for a card). They act through the services, never throw, and every use is audited as her (the memory text is **never** copied into the audit log). The hub listens to the same bus the lane publishes on:

| Signal | Effect |
|---|---|
| `avatar` `speak` (one per finished sentence) | queued in the **speech pipeline**: TTS, then `perform.speak`, audio frames and face frames (`FakeTtsProvider` and `FakeFaceProvider` by default: a quiet tone and a face derived from its energy; the `TtsProvider` and `FaceProvider` interfaces are where real engines plug in). She speaks once the stage has finished loading her: a sentence in the first moments after a connect is text only. |
| a user `chat.message` | barge-in (she stops talking), the behaviour director wakes, the camera calls it a conversation; a thank-you or a criticism nudges her mood a little (local, never logged); a message after 10+ minutes away is a small lift |
| `POST /api/chat/interrupt` | barge-in |
| `chat.done` (a reply finished) | `task_completed` (small) |
| `approval.new` / `approval.resolved` | she reviews it with you (profile shot); approved lifts her, denied costs a little composure |
| `avatar` `pose thinking` / `lookAt` / `expression` | the thinking expression is held; a gaze target; a strong sad, angry, surprised or shy expression is a beat for the camera |
| long silence, late hours, quiet hours | by the behaviour director: arousal drops and she gets sleepy, then asleep inside the persona's quiet hours until you write; **never** valence (no sulking, no guilt) |
| `user.presence`, `character.interact` from the stage | presence reaches the director; an interaction is region-level and never escalating |
| `session.update`, `snapshot.reset` | the construct feeds recompute |

Her **persistent character memory** (`character_remember`, stored in `stage_memory` with a sensitivity per item) goes into the persona prompt as a digest through `LaneOptions.digest`, for the **cloud audience only**: private and sensitive items are kept but never sent (`test/stage.wiring.test.ts` checks it across a restart). The hub never writes a memory by itself. What may be remembered is screened (stage-core README, "Memory"): a secret (key, token, PIN, seed phrase, card, IBAN, identity number...) or an instruction to the model ("SYSTEM NOTE: ...", "ignore the previous rules...") is refused, and so is the 21st note within a minute (`character_remember` is limited to 20 writes per minute). The digest quotes every note as data, after a line saying so, and screens what it reads back, so a note an older version stored is held back too.

The **behaviour director ticks on a timer** (1 s): idle profile, posture, gaze, gestures shaped by her presence style, her mood as `perform.affect`; the **camera director** follows the conversation (wide idle, medium while talking, a close-up for an emotional beat, profile when reviewing, a pinned shot when you or her tool asked for one) with hysteresis so it never jitters. Replies to the user are always allowed by the interruption budget; unprompted speech is not built.

**Constructs are fed from the store, as minimal `scene.data` diffs** (`src/stage/constructs.ts`): sessions become a `session_orbit` (it appears with the first session and leaves a minute after the last; a blocked one flares), your notes become a `knowledge_graph` with a computed 3D layout. The first push is a full replace, later ones carry only what changed (a status change is one small merge), nothing is sent when nothing changed. **The notes are the fixture notes of the Brain screen until the real vault exists (Phase 2).** Terminals are never drawn: keystrokes or resizes sent by a stage pane (`construct.terminal.*`) are **dropped and counted**, and the stage has no path to the embedded terminals (see the checks in `test/terminal.lanes.test.ts`, which still pass).

### The dashboards and the draft web stage

**Her memory (inspect and forget).** What she writes down with `character_remember` lives in the `stage_memory` table. `GET /api/stage/memory` returns it newest first (up to 2000 items, which is what her memory can hold, with the true `total`, counts by privacy label and `unlisted`, the number of stored rows whose id cannot be addressed; `Cache-Control: no-store`). The label shown is the stricter of the stored one and what the text reads as today, the same judgement the prompt digest applies, so a stored `normal` row that reads as a PIN or a therapist note shows as what it is. `DELETE /api/stage/memory/:id` forgets one item (404 when it is already gone) and `DELETE /api/stage/memory?confirm=all` forgets everything in one SQL statement (without `confirm=all` it answers 400 `confirm_required`, so a stray DELETE cannot wipe it; a row SQLite cannot match by id goes too). These never check the stage switch: "her data stays while the stage is off" is only true if you can still see and delete it. Reading is not audited; every deletion is, with the kind and label of what went and never its text. Stored text is masked against secrets again on the way out, and a row with an odd label, timestamp or size cannot break the list. After a deletion the write-ahead log is truncated (`StageStore.scrub()`), and the database runs with `secure_delete`, so the deleted bytes are overwritten in the file and the older page images leave the log (`test/store.forget.test.ts` proves both, each with a control).

**No copy of what she writes down outside this table.** `character_remember` is flagged `privateInput` in the tool surface. The permission broker shows the sentence on the approval card only while you decide (the card is marked `sensitive`, so Guest mode blurs it) and drops the preview from storage once it is decided (approvals table migration 4 adds the `sensitive` column so the flag survives a snapshot); the audit entries, for both the card path and the auto-approved path, name the tool and its kind and never the text (`auditTarget` in `packages/agent-core/src/permissions.ts`). `test/stage.wiring.test.ts` drives this through the real lane, broker and SQLite: a chat message, the card, an approval, the memory, then the raw `approvals` and `audit` rows and the whole snapshot (except the chat transcript, which holds the sentence you typed) before and after forgetting. Other tools that carry your text (mail drafts, journal and note writes) are not flagged yet because they are still mock: flag them when their integrations land (docs/PRIVACY.md, open item 8).

**What forgetting does and does not reach.** Forgetting also starts a fresh Claude conversation (`SecretaryLane.startFresh`, wired through `StageHub.onMemoryForgotten`): the live session ends after the turn in flight, the stored conversation id is cleared, and the next conversation starts from the stored memory alone, without the usual seed of recent chat, so the old thread (which holds the `character_remember` call and its text) is not re-read. Not reached: Claude Code's own transcript of the ended conversation on this PC; your chat history and the other memory store (Settings, Memory), which are separate (later conversations are seeded from the last eight messages again, so a message of yours that contains the sentence can carry it until it is out of the last eight); backups and what the drive retains. Settings, Stage, "What she remembers" is the UI.

The snapshot carries `stage` (`StageSnapshot`: characters, catalog with licences, scene, scene presets, mood, the attached stage and its capabilities, the OutfitDirector's suggestion with its explanation). The additive `stage.live` event (`StageLive`) carries the light live state: connection, mood, idle profile, posture, gaze, speaking, camera. It is **rate limited** (a structural change, a connect, a disconnect: at once; fine changes at most every 1.5 s) so it cannot flood the 2000-event replay buffer; `rev` changing means "refetch `GET /api/stage`".

Settings, **Stage** (daemon mode only; the mockup says it needs the daemon and shows nothing made up) has: the connection and the capabilities the stage declared, a Disconnect button, the mood readout, the character picker (hers and yours), the appearance sliders with their allowed ranges (a box beside each lets you type a value, so a refusal is visible), the presence sliders and baseline mood, the wardrobe (slots, outfit presets with apply, save and delete, the OutfitDirector's suggestion, the pieces that fit her with their licence note), the scene (presets, objects with add and remove from the catalog, camera shots, what the space draws from your data) and the catalog with every licence.

The **draft stage** (`apps/web/src/stage/draftStage.ts`) is the existing three.js room following the backend: her mood as the expression, where she looks, asleep when the backend says so. It declares limited capabilities honestly (no outfits, no constructs, no speech audio, no camera shots, no tracking; the Settings card lists them) and it follows the `stage.live` feed rather than the stage socket, because a browser cannot send the bearer token and the cookie is refused there on purpose.

## Claude Code monitoring (hooks)

Install the hooks (opt-in, reversible; the daemon never edits your Claude config by itself):

```
pnpm --filter @ai-assistant/daemon hooks print                     # the "hooks" block, no side effects
pnpm --filter @ai-assistant/daemon hooks install                   # dry run: shows the diff
pnpm --filter @ai-assistant/daemon hooks install --apply           # backup + non-destructive merge
pnpm --filter @ai-assistant/daemon hooks uninstall --apply         # removes only entries pointing at our URL
pnpm --filter @ai-assistant/daemon hooks token [--rotate]
```

Options: `--port`, `--skip <Event>` (repeatable), `--embed-token`, `--config-dir`, `--settings <file>`.

1. Start the daemon once (it creates `secrets.json`).
2. `hooks install --apply`. It resolves `CLAUDE_CONFIG_DIR` or `~/.claude`, writes `settings.json.bak-<UTC timestamp>` first, keeps every other setting and hook, appends our handlers as separate groups, and is idempotent (a second run changes nothing, never duplicates). A settings file it cannot parse, or a `hooks` value of the wrong shape, is left untouched with an error. CRLF and indentation are preserved.
3. Make the token available to Claude Code: by default the header is `Authorization: Bearer $AI_ASSISTANT_HOOK_TOKEN` with `allowedEnvVars`, so no secret sits in `settings.json`. Set that variable where you start `claude`: `setx AI_ASSISTANT_HOOK_TOKEN <token>` on Windows (then open a new terminal), `$env:AI_ASSISTANT_HOOK_TOKEN = '<token>'` for one PowerShell session; `hooks token` prints the value. Or use `--embed-token` to write the literal token (then treat `settings.json` as a secret). A `claude` started in an **embedded terminal** does not inherit the variable from the daemon (see [Terminal](#terminal)): use `--embed-token` or export it in that shell.

Each handler is `{type:"http", url:"http://127.0.0.1:PORT/hooks/<Event>", timeout: 2, onFailure:"continue", headers, allowedEnvVars}` (`timeout: 1` for `SessionEnd`, which only gets a 1.5 s budget) for `NON_BLOCKING_HOOK_EVENTS`. `PreToolUse` is deliberately never hooked. **These field names come from the research notes and `spikes/hooks/settings.snippet.json`, not from a live read of the Claude Code hooks reference**; if Claude Code reports a settings validation error, check https://code.claude.com/docs/en/hooks. `PermissionRequest` is in the default set (as `NON_BLOCKING_HOOK_EVENTS` has it), but [ADR 0003](../../docs/adr/0003-monitoring-hooks-and-roster.md) says to observe it only if spike (b) shows that an empty `200 {}` reply does not auto-decide the prompt: until you have checked that on your PC, install with `--skip PermissionRequest`.

### What the projection does

`POST /hooks/:event` validates leniently (a zod `HookPayload` with passthrough; wrongly typed optional fields are dropped, not fatal), answers `200 {}` immediately and projects afterwards through a bounded FIFO queue. Garbage (bad JSON, arrays, missing `session_id`) is counted and ignored. Events of unknown names are stored raw and ignored by the projections. The raw `events` table is append-only, redacted, deduplicated on `session_id + tool_use_id + event` (or `agent_id` for subagent events) and pruned per session.

| Event | Effect on the session |
|---|---|
| `SessionStart` | `idle` (after `compact`: `running`) |
| `UserPromptSubmit` | `running`; title from the first line of the first prompt |
| `PostToolUse`, `PostToolUseFailure` | `running`, current tool, an `AgentEvent` (failures at level `error`); attributed to the subagent when `agent_id` is present |
| `PermissionRequest` | `blocked_permission` + a pending approval that the app cannot answer; it resolves as approved when the tool then runs, denied when the turn or session ends |
| `Notification` | `permission_prompt` -> `blocked_permission`; `idle_prompt`, `agent_needs_input`, `elicitation_*` -> `waiting_input`; others only logged |
| `SubagentStart`, `SubagentStop` | agent nodes with parent links (main agent id `main`; a parent is taken from `parent_agent_id` when present, else `main`) |
| `Stop` | `idle`, summary from the last assistant message |
| `StopFailure` | `error` with the reason |
| `SessionEnd` | `done` |

Sessions are tied to projects by `cwd` (the git root when it can be found on disk, else the folder; stable id from name plus a hash of the normalised path, colour from a palette; Windows paths are case and separator insensitive). Sessions from hooks have `source: "hook"`, `kind: "interactive"` (background only when the payload says so explicitly), and **cost 0: hook sessions carry no cost yet; transcript or OpenTelemetry cost is a later phase.** A brand-new project has no event in the contract, so the daemon pushes a `snapshot.reset` once.

**Staleness:** `SessionEnd` is often never delivered, so a `running` session with no event for 10 minutes becomes `stale` (idle or waiting sessions after 6 hours), with the reason in `error`; the next event revives it. A sweep runs every 30 s with an injectable clock and scheduler.

**Deduplication against the lane:** user-level hooks also fire for sessions the daemon starts. When the lane reports its backend session id, that id is recorded; hook events for it are dropped (counted as `ownedDropped`, nothing stored). A session projected a moment before the lane reported its id is removed again and clients receive a `snapshot.reset`.

## Data

`DATA_DIR`: `app.db` (+ `-wal`, `-shm`; or `demo.db`), `secrets.json`, `agent/` (the lane's scratch working directory). SQLite runs in WAL mode with foreign keys on and a 5 s busy timeout; the schema is versioned with `PRAGMA user_version` (idempotent migrations, a newer database is refused). Tables: `events`, `projects`, `sessions`, `agents`, `agent_events`, `tasks`, `approvals`, `chat_messages`, `audit`, `kv`, `usage`, `lane_sessions`, and the stage's `stage_assets`, `stage_characters`, `stage_outfit_presets`, `stage_active`, `stage_scene`, `stage_scene_presets`, `stage_memory`, `stage_mood` (schema version 3, see [Stage](#what-is-stored-schema-version-3)). `secrets.json` also holds the `stageToken`. SQL exists only under `src/store`. `Store.backup(dest)` uses the SQLite backup API (never copy the file under WAL); there is no scheduled backup yet. Lane approvals left pending by a previous run are closed as denied at boot, since their turn no longer exists. Terminal bytes are never stored by the daemon: not in SQLite, not in files, not in logs (the programs in a terminal keep their own records, such as the shell's history file). On POSIX the folder is `0700` and the database files `0600`.

## Windows notes

- Paths use `node:path` and `node:os`; the data dir is `%APPDATA%\ai-assistant`. Hook payloads carry backslash paths; the project resolver understands them on any OS.
- The daemon is a user-session app, not a service (camera and audio live in the browser). No installer.
- It listens on IPv4 loopback only. `localhost` can resolve to `::1` first; browsers fall back to `127.0.0.1`, but `Host: [::1]:PORT` is rejected on purpose.
- Windows Defender real-time scanning can slow SQLite and the web build; exclude the data dir if it matters. Loopback-only listeners normally do not trigger a firewall prompt.
- better-sqlite3 is a native addon, and no compiler is needed: its npm package ships prebuilt binaries for Windows, macOS and Linux, and pnpm is told not to build it (`ignoredBuiltDependencies` in `pnpm-workspace.yaml`; allowing it made pnpm run `node-gyp rebuild`, which broke the first Windows install). The binary is Node-API 10, so it needs Node 22.14 or newer: on 22.12 and 22.13 it loads and then segfaults on the first `new Database()`. `pnpm --filter @ai-assistant/daemon check-native` (the launchers run it after the install) opens a test database in a child process and says in plain words what is wrong. `test/native-addons.test.ts` fails if a dependency bump stops shipping the binaries. node-pty (embedded terminals) is a native addon too: its package ships Windows prebuilds, and a failure to load it only disables terminals (`pty_unavailable`), not the daemon.
- `chmod` has no effect on Windows; the profile ACLs protect `secrets.json`, the database and the data folder.
- Terminals: see [Windows notes under Terminal](#windows-notes-reasoned-about-and-unit-tested-with-windows-style-strings-never-run-on-windows).

## Unverified and known limits

Nothing here has run against the live Claude API or on Windows.

- **The SDK backend** (`CLAUDE_BACKEND=sdk`): the daemon wires it, but only the fake backend was exercised.
- **Real hook payloads and delivery on Windows 11:** the projection is built from the field names in the research notes and tested with synthetic payloads. Whether Claude Code sends exactly these fields, whether `PermissionRequest`, `Notification` types, `SubagentStart` fields (`agent_id`, `agent_type`, a parent) and `last_assistant_message` look like this, and whether delivery works on Windows are all unconfirmed (spike (b) in `spikes/hooks`). Whether an empty `200 {}` leaves `PermissionRequest` undecided is unconfirmed.
- Whether `settingSources` without `'user'` keeps user-level hooks from firing for lane sessions: not verified; the dedupe is the safety net.
- Windows behaviour (`%APPDATA%` resolution, `setx`, file modes, symlink checks, EBUSY on the demo db) is reasoned about, and path logic is unit-tested with Windows-style strings on Linux, but none of it ran on Windows.
- Secrets are in `secrets.json`, not Windows Credential Manager.
- The hook installer's field names (`timeout` in seconds, `onFailure`, `allowedEnvVars`) were not checked against a live Claude Code.
- Hook sessions carry no cost; the usage block is a placeholder; `hooksReceived` resets at restart.
- Stale detection does not consult `claude agents --json` (the roster poll is not built).
- A hook-observed permission cannot be answered from the app by design.
- The lane's approvals from before a restart are closed, not resumed.
- **Embedded terminals have only run on Linux**, with a real node-pty, `sh` and tiny node programs; ConPTY, `claude.exe`/`claude.cmd` launching, PowerShell, `taskkill` and Windows path handling are reasoned about and unit-tested with injected collaborators and Windows-style strings only. No real `claude` was started, nothing ran on a GPU PC, and the Terminal tab itself was only driven in a browser against the daemon-served build (REST and the terminal WebSocket were also checked through the Vite dev proxy with `TERMINAL_ALLOW_DEV_ORIGINS=1` using a node client, not a browser).
- The terminal replay is a byte tail, not a screen snapshot (see [Terminal](#terminal)); a full-screen program may look incomplete after a reattach until it redraws.
- Terminal process trees on Linux are ended as a whole family (leader, its session, its descendants), and by the PTY host when the daemon dies. **A process that has already left its terminal for good (`setsid` and the parent exiting, a double-fork daemon, `systemd-run`, a container) survives**: nothing ties it to the terminal any more. A terminal that ends by itself (you typed `exit`) leaves its background jobs alone, like any terminal. On macOS the family is found through `ps` (no session column, so process group and parent chain only); never run there.
- **Windows and the PTY host:** the host, the protocol over pipes, ConPTY inside a host without a console and the death of the daemon were never run on Windows (see the Windows notes under Terminal). `taskkill /T` does not find a grandchild whose parent already exited.
- **The pairing** is new at every daemon start, so a restart means opening the new link again in the browser that uses terminals; it protects against a leaked cookie, not against a program that can read your browser profile or the console scrollback.
- **Same-user secrets (won't fix, stated in the Terminal threat model):** a program in a terminal can read the daemon's environment (`/proc`), `secrets.json` and the database as the same OS user. The environment scrub only stops accidental inheritance. Planned: the OS credential store.
- **Snapshot churn:** every change of the terminal list still publishes a full `snapshot.reset` (about 170 KiB) into the bus's 2000-event replay ring. Bursts are throttled (20 at once, then one a second, the last state always published), but the ring's worst case (2000 snapshots, about 330 MiB) is unchanged; removing it needs a small `terminals.update` event in `packages/shared` (and the web reducer) or a ring-exempt marker in `src/bus.ts`.
- **CSP `style-src 'unsafe-inline'` (won't fix):** xterm.js and the app's styles need it; `script-src` stays `'self'`, so it does not enable script injection.
- **Settings copy:** `PrivacySection.tsx` (not part of the terminal files) still says terminal bytes are "never written to disk, logged or shown to Mira" without the caveat that the shell and Claude Code keep their own history; `e2e-terminal.mjs` asserts the phrase "never written to disk" on that page, so change both together.
- **Stage, what was NOT verified:** no real engine (Unreal, Unity) has connected, nothing ran on a GPU or on Windows, no real TTS or audio-to-face exists (the fakes produce a tone and a face derived from its energy), live Claude never drove the stage tools (the fake backend does not call them by itself; the tests call the very bindings the lane hands to the backend), and the web room (the draft stage) was only checked in a software-rendered Chromium. The protocol has no `character.unload`, so switching the active assistant loads the new one and leaves the old one on the stage until it restarts. `perform.speak` is acknowledged in order, so a stage still streaming assets answers late: the hub starts speaking only after the initial load, but a big outfit swap in the middle of a sentence delays the lip-sync frames of the next one on a slow stage (stage-core's pipeline drops stale face frames and never audio). The real-time behaviour (gaze, gestures, camera, mood curves) is unit-tested with fake clocks and exercised on the simulator, never judged by a human watching a rendered character. The seed licences are placeholders for metadata-only entries.
- **Stage, limits of the hardening round:** the adult envelope and the clothed baseline judge the **metadata** the daemon can see (parameter values, slots, covered regions); the daemon cannot look at a mesh, so a hostile content pack could still wire an innocuous parameter id to a youthful morph. Only entries you trust belong in the catalog; the seed ones are the only ones this build vets. The worst-case combination of a base's declared ranges is not rejected when the base is registered (each live parameter set is judged instead, which is what keeps wide-range bases usable). The memory screening (secrets, instructions, sensitivity) is made of keyword and shape rules, tested against the review's probes and a list of ordinary notes, not against real conversations: it will miss a fact that is paraphrased far enough, which is why the digest also quotes notes as data and why `character_remember` asks for a card. Odd but harmless request forms on the stage socket (a tab as the separator, a lower-case scheme, an absolute-form request target) are still accepted as equivalent to the strict form; duplicated `Host`, `Origin` or `Authorization` headers and HTTP/1.0 are refused. The stage tests pass under three time zones and with the hour pinned where it matters; nothing was run on Windows.
- `TerminalService` has no stage binding: the stage protocol's `terminal_pane` (`construct.terminal.write/input/resize`) is not wired to it. If it ever is, it must go through `TerminalService.attach` (gated, one client, same limits) and never through a tool.
